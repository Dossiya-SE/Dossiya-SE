# Profile-wide Mathematical Presentation Standard — V3

**Purpose.** This document is the presentation, notation, provenance, and visual-integrity contract for mathematical content displayed across the `Dossiya-SE` GitHub profile and connected research repositories.

The objective is not to place more equations on pages. The objective is to make every displayed mathematical object **legible, interpretable, source-traceable, assumption-aware, computationally reproducible where applicable, and visually consistent with its scientific status**.

---

## 1. Scope and boundary

The profile spans sustainable engineering, infrastructure resilience, energy systems, quantitative finance, data science/machine learning, systems design, measurement/traceability, and scientific computing. No individual portfolio can literally display "all mathematics". The profile therefore uses a **curated mathematical architecture** that is exhaustive relative to the claims actually made in the repositories.

A mathematical object may appear in a repository only if at least one of the following is true:

1. it is directly used by implemented code or analysis;
2. it is part of an explicit research/model specification;
3. it is a source-grounded mathematical foundation needed to define the model;
4. it is clearly marked as a design target, extension, or hypothesis.

A formula is never used as decoration or as evidence of expertise by itself.

---

## 2. Canonical evidence states

Every major formula, visual, or model should be classifiable as one of:

| Tag | Meaning | Permitted language |
|---|---|---|
| **[S] Source-grounded** | faithful mathematical statement anchored to a source | "the source defines/states" |
| **[D] Derived** | algebraically/logically derived from declared assumptions | "derived under assumptions..." |
| **[M] Model** | modeling choice or mathematical abstraction | "we model/represent" |
| **[C] Computed** | numerical result generated by code | "computed using..." |
| **[V] Verified** | checked analytically, numerically, structurally, or by invariant | "verification passed..." |
| **[E] Empirical** | supported by observed/official/experimental data | "observed/estimated from..." |
| **[H] Hypothesis** | new proposition requiring testing | "we hypothesize/test whether..." |
| **[T] Target** | engineering/design requirement not yet validated | "design target..." |

The status must not silently change when a formula is copied from one repository to another.

## 3. Mathematical typography

### 3.1 Scalars, vectors, matrices, tensors, sets

Use:

- scalar: $x,\theta,t$;
- vector: $\mathbf x,\mathbf u,\boldsymbol\theta$;
- matrix/operator: $A,B,L,\mathcal A$;
- tensor components: $g_{ij},R^i{}_{jkl}$;
- sets: $\mathcal V,\mathcal K,\mathcal U$;
- probability: $\mathbb P$;
- expectation: $\mathbb E$;
- covariance: $\operatorname{Cov}$;
- variance: $\operatorname{Var}$;
- norm: $\lVert\cdot\rVert$;
- trace: $\operatorname{tr}$;
- determinant: $\det$.

Do not use plain text `P()` when $\mathbb P(\cdot)$ is intended as probability in formal mathematical exposition.

### 3.2 Units

Units are upright and separated from variables:

```math
P=50\,\mathrm{MW},\qquad t=24\,\mathrm{h}.
```

Never italicize unit symbols as if they were variables.

### 3.3 Differentiation

- ordinary time derivative: $\dot x$;
- arc-length derivative: $d/ds$;
- partial derivative: $\partial_i$;
- covariant derivative: $\nabla_i$ or source-consistent semicolon notation;
- stochastic differential: $dX_t$, never conflated with a finite difference.

### 3.4 Indicial conventions for differential geometry

When using the Sochi differential-geometry foundation (`SOCHI-DG-2017-UPLOADED`):

- Greek indices $\alpha,\beta,\gamma$ denote surface coordinates;
- Latin indices $i,j,k$ denote ambient-space/general components when following the source convention;
- notation changes must be declared rather than silently mixed.

The source-specific equation registry is maintained in `Dossiya-SE/Dossiya-SE-Dossiya-SE/sources/sochi_2017/`.

## 4. Formula display contract

A professional formula block should contain, in this order where appropriate:

1. **Name / role**
2. **Equation**
3. **Object definitions**
4. **Domain and assumptions**
5. **Interpretation**
6. **Evidence state**
7. **Verification or reproduction link**
8. **Source/provenance**

Example:

### Geodesic equation — [S]

```math
\frac{d^2u^\alpha}{ds^2}
+\Gamma^\alpha_{\beta\gamma}
\frac{du^\beta}{ds}
\frac{du^\gamma}{ds}=0.
```

**Domain.** Regular surface chart; arc-length parameterization in the source formulation; Levi-Civita connection associated with the metric.

**Interpretation.** Intrinsic locally straight motion on the surface. This equation does not by itself imply a globally shortest path.

**Provenance.** Sochi, Eq. 418, as registered in the mathematics ecosystem.

## 5. Visual mathematics grammar

Every profile visual must declare what geometry means.

| Visual primitive | Permitted mathematical meaning |
|---|---|
| node | subsystem, state, variable group, or graph vertex |
| edge | declared dependency/coupling, never unspecified causality |
| edge width | quantitative magnitude only when data/model defines it; otherwise categorical |
| arrow | direction of mapping, flow, influence, or computation |
| curve | state trajectory, geodesic, fitted function, frontier, or declared conceptual path |
| surface/manifold | feasible/admissible/viable state set or source-defined geometric object |
| contour | level set of a declared scalar field |
| color field | numerical scalar/vector category with explicit legend |
| uncertainty band/tube | declared interval, credible region, confidence region, ensemble envelope, or scenario range |
| dashed boundary | constraint/admissibility/uncertainty boundary with label |
| mesh/grid | coordinate chart, discretization, state-space reference, or computational mesh |
| tangent/normal/binormal | geometric frame only when mathematically defined |

### Prohibition

Do not use curvature-colored surfaces, vector fields, phase portraits, topology diagrams, or probability densities merely because they look advanced. If color, geometry, or motion does not encode a declared quantity, it is decoration and should be removed or explicitly labeled conceptual.

| Role | Visual family |

Exact hex values may vary for accessibility, but meaning must remain stable within a visual.

## 7. Differential-geometry visual standard

Differential geometry is used in two distinct ways and must not be conflated:

### A. Source mathematics

Examples include:

```math
g_{\alpha\beta}=\partial_\alpha\mathbf r\cdot\partial_\beta\mathbf r,
```

```math
\Gamma^\alpha_{\beta\gamma}
=\frac12g^{\alpha\delta}
\left(\partial_\beta g_{\gamma\delta}
+\partial_\gamma g_{\beta\delta}
-\partial_\delta g_{\beta\gamma}\right),
```

```math
K=\frac{eg-f^2}{EG-F^2},
```

and the Frenet–Serret frame

```math
\mathbf T'=\kappa\mathbf N,\qquad
\mathbf N'=\tau\mathbf B-\kappa\mathbf T,\qquad
\mathbf B'=-\tau\mathbf N.
```

These are mathematical objects in their own right.

### B. Research transfer

Using a viability boundary, recovery path, or interface-uncertainty set as a manifold is a **modeling/research hypothesis** unless a precise differentiable structure and metric are actually defined.

The visual must therefore distinguish:

```text
source differential geometry  ≠  geometric metaphor  ≠  formally defined research manifold
```

## 10. README equation standard

For GitHub READMEs, prefer GitHub-supported display math:

````markdown
```math
\dot{\mathbf x}=\mathbf F(\mathbf x,\mathbf u,t;\theta).
```
````

Use inline `$...$` only for short symbols and avoid dense equations in table cells where rendering becomes fragile.

Long derivations belong in dedicated `.md`, `.tex`, notebook, or report files, not in the root README.

---

## 11. Website equation standard

The portfolio website uses MathJax. Every formula panel should provide:

- semantic heading;
- MathJax-rendered equation;
- plain-language interpretation;
- evidence-state tag;
- link to the repository containing implementation or source specification.

MathJax is presentation; it is not mathematical verification.

---

## 12. Accessibility and rendering

All SVG mathematical assets must contain:

```xml
<title>...</title>
<desc>...</desc>
```

and must use a `viewBox` so they scale without rasterization.

Requirements:

- legible at approximately 768 px width;
- no information encoded by color alone;
- adequate contrast in both GitHub light and dark environments where possible;
- labels not smaller than the practical equivalent of ~12 px at native display size;
- no clipped equations;
- arrows must have enough separation to reveal direction;
- line weights must remain visible after downscaling.

## 13. Formula provenance chain

Every stable formula should be traceable through:

```text
formula ID
→ source / derivation
→ assumptions
→ repository role
→ code implementation (if any)
→ verification test (if any)
→ visual representation (if any)
→ research/decision claim
```

The machine-readable registry is `formula_registry.json`.

---

## 14. Verification hierarchy for visual mathematics

A visual can be promoted through the following levels:

| Level | Requirement |
|---|---|
| **P0 Conceptual** | semantic labels and explicit "conceptual" status |
| **P1 Formula-consistent** | displayed relationships match declared equations |
| **P2 Numerically generated** | geometry/fields generated from code |
| **P3 Invariant-checked** | known identities/invariants pass |
| **P4 Source-reproduced** | source result independently reproduced |
| **P5 Empirically validated** | visualized model outputs validated against relevant data |

A visually sophisticated P0 graphic is still P0.

---

## 15. Scientific integrity rules

1. **No formula without a role.**
2. **No geometry without semantics.**
3. **No color without an encoded meaning.**
4. **No simulation presented as observation.**
5. **No source theorem presented as original contribution.**
6. **No research hypothesis presented as established mathematics.**
7. **No software test presented as empirical validation.**
8. **No optimization before constraints and objective are stated.**
9. **No probability without a defined random object/event.**
10. **No uncertainty band without a declared construction.**
11. **No causal arrow unless causal meaning is supported; otherwise use dependency/mapping language.**
12. **No visual ranking without scale, criterion, and evidence state.**
