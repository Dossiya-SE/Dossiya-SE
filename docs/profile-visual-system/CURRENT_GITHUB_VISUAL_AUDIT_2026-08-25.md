## 1. Audit scope

This audit covers the public profile README, its profile-facing mathematical assets, the visual-governance standards that control those assets, the account-wide mathematics-surface audit, the current account/repository architecture evidence available in GitHub, and open profile PRs that materially affect the visual system.

The audit does **not** treat successful SVG/TeX rendering as proof of scientific correctness or empirical validity. It also does not expose private-repository content beyond names, roles, and evidence boundaries already surfaced by the public profile/account-governance material.

The governing distinction is:

```text
visual correctness != mathematical correctness
mathematical correctness != empirical validity
visual similarity != scientific equivalence
```

## 4. Principal strengths to preserve

### 4.1 Evidence discipline is already a defining identity

The public profile explicitly uses a non-compensatory evidence invariant and repeatedly distinguishes source mathematics, models, computations, verification, validation, and empirical evidence. This is a major strength and should remain visually central.

### 4.2 Adaptive SVG infrastructure already exists

Most V5/V6 visuals use `viewBox`, `<title>`, `<desc>`, internal CSS tokens, and `prefers-color-scheme`. This is a strong GitHub-native base. The architecture should extend it rather than replace the profile with fixed dark PNG posters.

### 4.3 Differential-geometry transfer is bounded

The existing profile correctly states that geometric language applied to infrastructure requires a formally defined state-space geometry. The new visual system must preserve that boundary. No manifold, curvature, or geodesic language may be added to an application visual merely because it looks sophisticated.

### 4.4 Optimization V6 demonstrates the target semantic-color direction

`optimization-decision-system-v6.svg` is materially more mature than the earlier mostly monochrome-green V5 family. It uses distinct semantic colors for source/model, state, uncertainty, viability, decision, interface, and computed quantities while maintaining dark/light adaptation. That direction should inform the future profile-wide palette.

### 4.5 Account-wide math-surface quality is already largely controlled

The existing 16-repository mathematics-surface audit reports all 16 repositories inventoried, 637 Markdown/MDX files audited, 1,491 formulas checked with MathJax and strict KaTeX, and zero active high-confidence mathematics-rendering findings after verified repairs. The next visual-system work should therefore focus on **semantic visual integration and reproducible generation**, not on pretending the account lacks mathematical depth.

## 5. Critical findings

### V-01 — Hero is not a true editable/adaptive mathematical master — CRITICAL

`profile-header-v5.svg` contains a single embedded JPEG image. The current adaptive audit script scans `*-v5.svg` files and requires adaptive-theme tokens/query structure; the hero itself does not contain that structure. Independently of CI status, the asset is structurally inconsistent with the future canonical-SVG/editability contract.

**Required action:** rebuild the hero from separate editable semantic layers. Raster optical effects, if retained, must have explicit source/provenance and cannot be the only scientific content layer.

### V-02 — Existing V5 family is visually coherent but semantically under-colored — HIGH

The mathematics universe, research operating system, differential geometry, computational stack, formula–evidence lattice, evidence maturity map, and trajectory mostly use a narrow green palette. The repository's newer semantic-color ontology distinguishes source mathematics, observed evidence, state/dynamics, interfaces, uncertainty, viability, recovery/control, optimization/decision, computed quantities, and hypotheses.

**Required action:** move the full profile to the semantic ontology already demonstrated in V6. Color must always be reinforced by shape/line/label so no meaning depends on color alone.

### V-03 — Research operating system is scientifically outdated — CRITICAL

The current profile visual encodes an older eight-node chain. The newly frozen scientific-research architecture is substantially richer. Keeping the old compact figure as the signature process visual would visually understate gap architecture, research questions, assumptions, provenance, verification/calibration/validation separation, sensitivity/UQ, comparison, limitations, and reproducibility.

**Required action:** rebuild as the main profile signature architecture.

### V-04 — Current visual families are not yet one mathematical system — HIGH

The figures share style but not a common machine-readable object graph. A trajectory node, evidence node, uncertainty band, validity boundary, and repository node do not yet have one stable cross-visual semantic ID scheme.

**Required action:** freeze global object IDs, visual grammar, semantic palette, typography tokens, and source/provenance registry before generating successors.

### V-05 — Differential geometry must be computation-driven — HIGH

The current visual communicates correct source concepts and transfer boundaries, but the target protocol requires genuine geometry where geometry is claimed. The existing verified geometry engine already provides a route to a P3 invariant-checked artifact.

**Required action:** generate the successor from symbolic/numerical geometry and export renderer-neutral geometry before SVG composition.

### V-06 — Evidence ontologies can currently be confused — HIGH

Two useful vocabularies coexist:

```text
Evidence lifecycle/state:
[S] source-grounded
[D] derived
[M] model
[C] computed
[V] verified
[E] empirical
[H] hypothesis
[T] target

Object provenance/status:
USER_SPECIFIED
OBSERVED
PUBLISHED
COMPUTED
CALIBRATED
DERIVED
ASSUMED
SYNTHETIC
ILLUSTRATIVE
TO_BE_VALIDATED
```

They are not interchangeable. For example, a `COMPUTED` provenance object can still be in a model-level evidence state rather than empirical evidence.

**Required action:** keep two explicit orthogonal fields in the machine-readable registry: `provenance_class` and `evidence_state`.

### V-07 — Profile README is becoming too much like a second portfolio site — HIGH

The README already carries many full-width figures and long technical narratives. The account-governance audit separately identifies the need for a strict division between the concise profile front door and `dossiya-se.github.io` as the interactive portfolio.

**Required action:** future README redesign should emphasize a compact hierarchy: identity → research programmes → mathematical operating system → selected signature visuals → repository navigation. Deep technical narratives should link outward.

### V-08 — Legacy visual-version sprawl weakens source authority — MEDIUM/HIGH

Multiple unversioned, V3, V4, V5, and V6 files coexist in the active `assets/math-art/` directory.

**Required action:** after each new successor passes, move superseded versions to `assets/math-art/archive/<family>/`; keep one canonical current master plus its reproducibility package.

### V-09 — Repository-navigation mathematics is missing — HIGH

The account contains 16 repositories with distinct roles, but the profile lacks a single mathematical graph explaining their relationships. Existing account audits identify fragmentation and multiple front doors as the dominant account-level risk.

**Required action:** create a repository-role knowledge graph with explicit layer semantics and no unsupported quality ranking.

### V-10 — Branch/release governance remains a publication risk — HIGH

The current `main` branch is not protected. Open PRs also include a hero replacement PR and an editable-render-contract PR. These are relevant to the visual migration because multiple competing profile states can remain unresolved.

**Required action:** no profile-wide visual migration may merge automatically. Architecture, renderer contract, individual visual releases, and README integration must remain separate reviewable gates.

## 8. Audit conclusion

The profile does **not** need a decorative redesign. It needs a controlled migration from a collection of strong adaptive figures to one mathematically generated, scientifically governed, reproducible identity system.

The architecture should therefore preserve the strongest existing concepts while rebuilding the following foundations:

```text
one global semantic grammar
+ one semantic color ontology
+ one object-ID namespace
+ one equation/data/provenance registry
+ one canonical adaptive SVG master per visual family
+ one fail-closed QA/reproduction path
+ one repository-role graph for the full account
```
